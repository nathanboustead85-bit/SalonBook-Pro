# Phase 36.2 — Isolated Firebase verified-owner session integration

The `createVerifiedOwnerSession` bridge combines an injected Firebase Auth SDK instance, forced `getIdTokenResult(user,true)`, the real Android business document reader from Phase 36.1, and the fail-closed Phase 35.3 auth lifecycle. A verified session requires matching token `user_id`, `email_verified:true`, a verified user object, and a future ID token expiration time. Session changes, sign-out, token errors, expiry and network failures clear private dashboard data. No bookings, payments, messaging, edits or deployment.

Tests run a **real Firebase Auth emulator** with a synthetic account and email-verification update through the emulator's fake-key Identity Toolkit endpoint, plus real Firestore emulator rules under the same isolated demo project. Firestore owner/verified claims are supplied by `@firebase/rules-unit-testing` contexts; **these tests do not demonstrate a live Auth token directly authenticated to Firestore**. The bridge does not register a real `onIdTokenChanged` listener; callers must explicitly forward changes via `authChanged`. Token revocation, App Check, real-device auth listener lifecycle, production connectivity and genuine backend outage testing remain launch blockers. No production Firebase rules/config modified. Original Android appointments remain untouched.
